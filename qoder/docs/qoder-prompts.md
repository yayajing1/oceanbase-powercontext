# Qoder 开发记录：分阶段提示词与作用说明

> 本文件记录「研读台 PaperDesk」项目**在 Qoder 中完成开发**的全过程。
> 每个阶段对应一次 Qoder 会话（Qoder CLI / IDE 均可复现），下面是实际投喂给 Qoder
> 的提示词原文，以及 Qoder 在该阶段产出的文件。
> 原始对话记录见 `records/qoder-sessions/`（机器可读的 stream-json transcript），
> 以及本机 Qoder 会话库 `~/.qoder/projects/<project>/<session-id>.jsonl`。

## 0. 为什么分成这些阶段

赛题要求「项目的主要开发工作必须在 Qoder 中完成」，并且要能核对 Qoder 在
**需求拆解、编码、调试**三个环节中做了什么。因此把开发拆成 7 个有明确产出物、
可独立验收的阶段，每个阶段都以「上一阶段的产出 + 本阶段的任务」作为上下文，
形成一条可追溯的链路：

```
阶段1 需求拆解        → docs/technical-design.md
阶段2 数据层与导入    → paperdesk/{config,db,chunking,importer}.py
阶段3 混合检索        → paperdesk/{search,textnorm}.py
阶段4 卡片与复习      → paperdesk/{cards,review}.py
阶段5 记忆与跨会话    → paperdesk/{memory}.py
阶段6 综述提纲与 CLI  → paperdesk/{outline,cli}.py + tests/
阶段7 站点源码        → site/
```

每个阶段结束后由人（评审者视角）复核产出物，发现问题就以「反馈轮」的形式追加
提示词让 Qoder 修正——这些反馈轮同样记录在 `records/qoder-sessions/` 中，
用于证明 Qoder 参与了调试环节。

## 阶段 1 · 需求拆解

**提示词原文**

```
请先阅读 `qoder/PRD.md` 和 `qoder/data/sample_notes/` 下的样例数据。

这是「研读台 PaperDesk」项目的第一步：**需求拆解**。

请完成以下事情：
1. 阅读 PRD 全文，并在 `qoder/docs/technical-design.md` 写出一份技术设计文档，内容包括：
   - 模块划分（建议的 Python 包结构与每个模块职责），以及每个模块对外的命令/函数入口；
   - seekdb 的数据模型：需要建哪些表、每张表的列、类型与索引设计（重点说明全文索引怎么建、怎么保证中文可检索）；
   - PowerContext 的使用设计：存哪些记忆项、用什么类型/接口存、如何落盘、读回后在哪些流程里生效；
   - 数据流：从「导入 Markdown 笔记」到「生成卡片」「进入复习队列」「输出综述提纲」的完整链路；
   - 你认为 PRD 里没写清楚、需要做的技术取舍（列成清单，每条给出你的选择和理由）。
2. 暂时**不要**写业务代码，这一轮只出设计文档。
3. 不要修改 `qoder/PRD.md` 和 `qoder/data/` 下的任何文件。
```

**Qoder 在这一步做了什么**：把 PRD 的功能清单翻译成可实现的模块边界，
给出 seekdb 的表结构与全文索引方案，确定 PowerContext 存三类记忆
（用户画像 / 复习记录 / 薄弱点）以及它们各自的生效点，并列出 PRD 未明确的
取舍（切块长度、卡片字段的默认值、复习间隔算法参数等）。

## 阶段 2 · 数据层与文献导入

**提示词原文**

```
按 `qoder/docs/technical-design.md` 的设计开始实现。本轮只做「数据层 + 文献导入」：

1. 在 `qoder/paperdesk/` 下建立 Python 包 `paperdesk`，实现配置读取、数据库连接
   与建表（seekdb / OceanBase，MySQL 协议，连接参数全部走环境变量）。
2. 实现 Markdown 笔记导入：
   - 解析 YAML front matter（title / authors / year / tags）以及正文里的
     `## 问题` `## 方法` `## 结论` 小节；
   - 按标题层级切块，没有标题时按段落切块，单块不超过可配置的最大字符数（默认 800）；
   - 记录每块的来源文件、起止行号；
   - 幂等：同一文件重复导入不产生重复块，文件内容变化后被删掉的旧块必须消失
     （用内容指纹 + 清理过期块实现）。
3. 为块字段建**原生全文索引**，保证中文关键词可被 MATCH 命中。
4. 写单元测试：不依赖数据库的解析/切块逻辑用 pytest 覆盖。

约束：
- 不提交任何真实凭据，连接参数用环境变量 + `.env.example` 占位；
- 数据库连接串默认 `127.0.0.1:2882`，库名可用环境变量 `PAPERDESK_DB_NAME` 覆盖；
- 现在只实现这一部分，检索、卡片、复习等后续功能先不要做。
```

**Qoder 在这一步做了什么**：写出 front matter 解析、正文分节、行号回溯的切块器，
定义了块指纹字段与清理策略，给出建表 DDL 与 `FULLTEXT` 索引的建法，
并补上不依赖数据库的解析单测。

## 阶段 3 · 混合检索

**提示词原文**

```
继续实现「混合检索」功能：

1. 一次查询同时使用两类能力，并把结果合并：
   - 关键词全文检索：在 seekdb 的原生全文索引上做 MATCH，中文必须能命中；
   - 结构化条件过滤：年份区间、标签（多选 OR）、作者。
   两者必须在**同一条 SQL** 里同时生效（全文条件写在 MATCH 中，结构化条件写在
   WHERE 中），不允许在应用层把全表拉出来自己算匹配。
2. 返回结果必须包含：片段正文、出处（来源文件 + 起止行号）、相关度分数，
   以及标明该条是被全文命中还是被结构化条件命中。
3. 搜索词要做归一化：去掉标点、统一大小写、中英文之间加空格，保证中文子串
   能正确命中全文索引。
4. 提供一个 `explain` 开关，能打印出实际执行的 SQL 与 EXPLAIN 结果，
   便于核对原生索引确实被使用。
5. 补测试：至少一条中文关键词命中的用例、一条年份+标签过滤用例。

不要动导入和切块逻辑。
```

**Qoder 在这一步做了什么**：把归一化、SQL 拼装、执行计划打印串起来，
让「全文命中 / 结构化命中」两种来源在输出里可区分，并留下 EXPLAIN 入口。

## 阶段 4 · 研究卡片与复习队列

**提示词原文**

```
继续实现「研究卡片」与「复习队列与掌握度」：

1. 卡片字段固定为：问题 / 方法 / 结论 / 与我的工作的关系 / 来源片段 id。
   - 生成卡片时若没有配置模型 API（环境变量 `PAPERDESK_MODEL_API_KEY` 等），
     必须给出明确提示并允许用户手工填写，而不是静默产出空卡片；
   - 模型调用做成可插拔：没有模型时走「手工填写」路径，两条路径都要能用。
2. 卡片入库，可按卡片检索，可修改、可删除。
3. 复习队列：卡片可加入队列；每次复习给 0~5 的掌握度评分，
   系统据此计算下次复习时间（评分越高间隔越长，评分 0 则当天重来）。
   队列要展示：今天该复习的卡片、每张卡片的掌握度、下次复习时间。
4. 补测试：卡片 CRUD、掌握度评分到下次复习时间的计算（含评分 0 的边界）。
```

**Qoder 在这一步做了什么**：设计了卡片的增删改查与检索，
实现了无模型时的降级路径与提示文案，实现了间隔重复算法及其边界测试。

## 阶段 5 · PowerContext 记忆与跨会话复用

**提示词原文**

```
继续实现「记忆与跨会话复用」，这一轮接入 PowerContext：

1. 用 PowerContext（进程内 Core SDK：`powercontext.builtin.runtime.open_builtin_runtime`，
   文件后端，默认落在 `qoder/.state/powercontext.db`）保存三类记忆：
   - 用户画像：研究方向、常用标签、当前在写的综述主题；
   - 复习记录：每张卡片的评分历史、下次复习时间；
   - 薄弱点：被评低分的卡片对应的标签/主题。
2. 记忆必须**落盘**，进程重启后能读回（不是内存临时变量）。
3. 读回的记忆必须**真的影响输出**，并在输出里**标明**哪些部分来自记忆：
   - 检索时用画像里的标签做加权/过滤提示；
   - 复习队列用复习记录直接给出待复习清单（而不是空队列）；
   - 薄弱点在队列/推荐里主动提示「这些主题你不熟」。
4. 提供一个 `memory show` 子命令把当前记忆原样打印出来，便于核对。
5. 补测试：写入记忆 → 换进程（新开 runtime 实例）读回 → 输出中可见影响。

PowerContext 是赛题要求的指定技术，必须真实参与功能，不能只装组件测连接。
```

**Qoder 在这一步做了什么**：把三类记忆映射到 PowerContext 的
content Source / Task Outcome 双写结构，实现了进程级落盘与读回，
并让检索加权、复习清单、薄弱点提示三处真正消费记忆内容。

## 阶段 6 · 综述提纲、CLI 入口与端到端验证

**提示词原文**

```
继续实现「综述提纲」与统一的 CLI 入口，并补齐测试：

1. 综述提纲：按标签 / 年份 / 作者聚合已有卡片，输出结构化 Markdown 提纲，
   每条提纲后面附上支撑它的卡片（标题 + 出处）。
2. CLI 入口（`python -m paperdesk` 或 `paperdesk`），子命令至少包括：
   `init-db` / `import` / `search` / `card` / `review` / `memory` / `outline` / `demo`。
   每个子命令都要有 `--help` 说明输入与输出。
3. 端到端验证脚本 `qoder/validation/run_validation.py`：
   从空库开始，导入样例笔记 → 检索（中文关键词 + 结构化过滤）→ 生成卡片 →
   加入队列 → 打分 → 重新启动进程 → 读回记忆与待复习清单 → 输出综述提纲，
   每一步打印预期与实际，最后给出 PASS/FAIL 汇总和退出码。
4. 补单元测试：切块、归一化、复习算法、提纲聚合。

注意：不要把模型 API Key、数据库密码写进代码或提交物。
```

**Qoder 在这一步做了什么**：完成提纲聚合、统一 CLI 与端到端脚本，
使「导入→检索→卡片→复习→重启→记忆复用→提纲」成为一条可重复执行的链路。

## 反馈轮（调试环节）

实现过程中发现并回抛给 Qoder 的问题示例（实际对话见 `records/qoder-sessions/`）：

- **反馈 1**：中文关键词检索不到结果 —— 因为分词器把「图对比学习」切开后
  MATCH 表达式不合法；要求 Qoder 改成「归一化 + 逐词 OR + 退化为 LIKE」的多级策略。
- **反馈 2**：重复导入产生重复块 —— 指纹字段选错；要求改为按「文件路径 + 块序号 +
  内容哈希」判定，并在导入结束时清理该文件下已不存在的旧块。
- **反馈 3**：重启进程后复习队列为空 —— 复习记录只写进了内存；
  要求改为写 PowerContext 并在 `review` 子命令启动时读回。
- **反馈 4**：端到端脚本在干净环境退出码非 0 —— 数据库连接失败时没有给出可操作提示；
  要求补上连接诊断与退出码约定。

这些反馈轮证明 Qoder 不只是「一次性生成代码」，而是在真实调试中被反复调用。
